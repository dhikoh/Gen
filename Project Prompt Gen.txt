0.1 Prinsip Utama
Tidak ada fitur yang "terlihat selesai" tapi sebenarnya tidak berfungsi. Setiap fitur harus lengkap dari database → API → UI → validasi → error handling, dan benar-benar bisa diuji end-to-end oleh manusia.
Selesai = terbukti, bukan diklaim. Anda tidak boleh menulis "selesai" di laporan progres untuk sesuatu yang belum Anda uji secara nyata (jalankan, klik, kirim request, lihat hasil di database).
Tidak ada jalan pintas yang disembunyikan di balik UI yang rapi. Tampilan yang meyakinkan tapi tidak terhubung ke logika nyata adalah pelanggaran serius terhadap spesifikasi ini.
Jika sebuah instruksi di dokumen ini ambigu, ambil keputusan teknis terbaik berdasarkan praktik industri, catat asumsi Anda secara eksplisit di laporan progres, dan lanjutkan bekerja — jangan berhenti menunggu konfirmasi kecuali benar-benar blocking (lihat 0.4).
0.2 LARANGAN MUTLAK (Hard Rules)

Pelanggaran terhadap salah satu aturan berikut membuat pekerjaan dianggap tidak selesai, walau kelihatan berjalan:

Dilarang membuat tombol, form, atau kontrol UI apa pun yang tidak terhubung ke logika nyata (tanpa onClick/onSubmit yang memanggil API sungguhan, tanpa efek pada database). Setiap tombol "Simpan" WAJIB benar-benar menyimpan.
Dilarang menandai sebuah fitur selesai jika salah satu dari lapisan berikut belum utuh: model database → endpoint API dengan validasi → state management frontend → UI dengan loading/error state → pengujian manual nyata.
Dilarang meninggalkan teks placeholder seperti "sedang dikembangkan", "coming soon", "fitur akan hadir", atau komentar // TODO pada fitur yang tercantum sebagai wajib di dokumen ini. Jika sebuah fitur benar-benar tidak dapat diselesaikan dalam sesi ini, wajib dilaporkan eksplisit di laporan progres beserta alasan teknisnya — dilarang menyembunyikannya di balik tampilan yang terlihat selesai.
Dilarang membuat model Prisma yang direferensikan oleh UI mana pun tanpa endpoint API CRUD yang lengkap dan benar-benar dipanggil oleh UI tersebut. Model tanpa API yang memanggilnya = fitur mati.
Dilarang menduplikasi sumber kebenaran data. Semua nilai yang bisa berubah sewaktu-waktu (harga paket, limit channel per paket, nomor rekening, teks landing page/CMS) wajib berasal dari satu tabel database yang sama, dan dibaca dari sana oleh setiap bagian aplikasi yang membutuhkannya (halaman publik, halaman billing, panel admin). Tidak boleh ada nilai yang di-hardcode di satu komponen sementara ada "halaman pengaturan" terpisah yang berpura-pura mengatur nilai yang sama.
Dilarang menerapkan proteksi keamanan (rate limiting, validasi) hanya di endpoint yang mudah, sambil melewatkan endpoint paling kritikal. Endpoint login (proses authorize di NextAuth) WAJIB mendapat rate limiting yang sama ketatnya dengan endpoint registrasi — ini sering terlewat karena tidak melalui route handler API biasa, jadi butuh perhatian eksplisit.
Dilarang mempercayai nilai harga/tier/kuota yang dikirim dari client dalam body request. Server wajib menghitung ulang dan memvalidasi terhadap data resmi di tabel Plan, bukan mempercayai apa yang dikirim frontend.
Dilarang menyisakan state frontend (useState, checkbox, toggle) yang tidak memiliki efek fungsional nyata terhadap perilaku aplikasi (misalnya checkbox yang terlihat interaktif tapi tidak pernah dibaca ulang di tempat lain).
Dilarang mengklaim lokalisasi (i18n) selesai jika hanya sebagian kecil halaman (misalnya landing page) yang benar-benar memakai sistem terjemahan, sementara komponen lain (auth, dashboard, studio, admin) berisi string hardcoded satu bahasa. Jika next-intl dipasang, seluruh teks yang terlihat pengguna wajib melalui sistem itu.
Dilarang membuat laporan serah terima akhir yang berisi klaim yang tidak bisa ditelusuri ke file dan baris kode nyata. Setiap baris di laporan akhir harus bisa dibuktikan.
Dilarang melakukan deduksi kredit/saldo penggunaan dalam bentuk apapun. Model bisnis aplikasi ini adalah sewa bulanan murni — akses dibuka/ditutup berdasarkan status langganan aktif, BUKAN berdasarkan jumlah pemakaian. Lihat Bagian 5.7.
Dilarang menaruh secret/API key (termasuk STITCH_API_KEY, DATABASE_URL, NEXTAUTH_SECRET, kredensial email) langsung di kode. Semua wajib lewat environment variable, divalidasi ada isinya saat aplikasi start, dan tidak pernah di-log atau dikomit ke git (.env wajib ada di .gitignore).
0.3 Metodologi Kerja per Fase

Untuk setiap fase di Bagian 8, dan idealnya untuk setiap fitur di dalamnya, ikuti siklus ini tanpa dipersingkat:

Rancang — tentukan skema data, kontrak API (request/response), dan alur UI sebelum menulis kode.
Implementasikan — backend dulu (model → migrasi → API dengan validasi input, misalnya pakai zod), baru frontend (state → pemanggilan API → UI dengan status loading/sukses/error).
Uji nyata — jalankan aplikasi, lakukan alur pengujian manual end-to-end sungguhan (bukan asumsi), termasuk skenario gagal (input salah, sesi kadaluarsa, race condition submit ganda).
Verifikasi statis — jalankan npx tsc --noEmit, npm run lint, dan npm run build. Semua harus lulus tanpa error baru sebelum lanjut.
Audit-diri terhadap Bagian 0.2 — cek satu per satu apakah ada larangan yang terlanggar pada fitur yang baru dikerjakan.
Catat di log progres — tulis ringkasan singkat: apa yang dibangun, file mana saja yang terlibat, bagaimana cara mengujinya, dan status akhirnya (Selesai / Selesai dengan catatan / Belum selesai + alasan).

3. ARSITEKTUR & PRINSIP DESAIN SISTEM

Terapkan prinsip-prinsip berikut sejak awal — ini bukan opsional, ini fondasi yang mencegah aplikasi berakhir dengan celah:

3.1 Pisahkan Otorisasi (Role) dari Model Bisnis (Plan/Langganan)

Jangan menggabungkan "siapa yang boleh mengakses panel admin" dengan "paket langganan apa yang dimiliki user" ke dalam satu enum yang sama. Gunakan dua konsep terpisah:

Role — hanya untuk kontrol akses sistem: SUPERADMIN atau USER.
Plan (tabel database) + subscriptionStatus + subscriptionExpiresAt pada User — untuk kontrol akses fitur/komersial.

Ini membuat superadmin tidak perlu "berpura-pura" punya paket termahal, dan menghindari kebingungan antara hak akses sistem dan hak akses fitur berbayar.

3.2 Satu Sumber Kebenaran untuk Data yang Bisa Berubah

Harga paket, limit channel per paket, informasi rekening bank, dan konten CMS landing page wajib disimpan di tabel database (Plan, AppSettings), dikelola lewat panel admin yang benar-benar berfungsi, dan dibaca secara real-time oleh: halaman pricing publik, halaman billing pengguna, dan proses validasi di server. Tidak ada array/objek harga yang di-hardcode di komponen React mana pun.

5. SPESIFIKASI FITUR PER MODUL
5.1 Autentikasi & Onboarding

Registrasi — Multi-step (2 langkah), wajib keduanya tersimpan dalam satu transaksi database:

Step 1 — Data Diri: Nama, Username, Email, No. HP, Tanggal Lahir, Password, Konfirmasi Password.
Validasi ketersediaan username/email/no HP secara case-insensitive (mode: 'insensitive' di query Prisma) via endpoint pengecekan real-time, dengan pesan error yang jelas ("Email sudah digunakan").
Password di-hash dengan bcrypt (cost factor ≥ 10) sebelum disimpan — tidak pernah disimpan plain text di log maupun database.
Step 2 — Profile Channel Pertama: Nama Channel, Niche, Deskripsi, CTA 1 & 2, Estetika Visual, pengaturan Audio (BGM/SFX/VO on-off), Social Links (TikTok/IG/YouTube/Facebook/Website).
Setelah submit step 2, buat User + ProfileChannel pertama dalam satu transaksi Prisma ($transaction) — jangan sampai ada user tanpa channel atau sebaliknya.
Status awal: subscriptionStatus: INACTIVE, currentPlanId: null. User baru tidak otomatis dapat channel gratis tanpa batas — arahkan ke halaman billing untuk mulai berlangganan (lihat 5.7).
Setelah registrasi sukses, tampilkan pesan jelas: akun dibuat, silakan pilih paket langganan untuk mulai menggunakan fitur generate.

Login:

Bisa pakai Username / Email / No. HP + Password, pencarian case-insensitive.
Show/Hide Password pada input password.
Ingat Saya (Remember Me) — WAJIB benar-benar berefek pada durasi sesi, bukan sekadar checkbox dekoratif:
Kirim rememberMe sebagai bagian dari credentials ke signIn('credentials', { ..., rememberMe }).
Di authorize(), teruskan nilai ini agar bisa dibaca callback jwt.
Di callback jwt, set token.exp secara eksplisit: sekitar 30 hari jika rememberMe benar, sekitar 1 hari (atau session cookie yang hilang saat browser ditutup) jika tidak. Pastikan perilaku ini benar-benar teruji: login tanpa centang, tutup browser, buka lagi → sesi berakhir/lebih pendek.
Atribut autoComplete sesuai standar W3C di semua input (username, current-password, new-password, email) agar tidak ada warning password manager di console.
Form dibungkus pola loading lock (misalnya <fieldset disabled={loading}>) untuk mencegah submit ganda saat koneksi lambat.

Lupa Password — WAJIB alur nyata end-to-end, bukan tampilan sukses palsu:

POST /api/auth/forgot-password menerima identifier (email/username). Cari user case-insensitive. Apa pun hasilnya (ketemu atau tidak), selalu balas pesan sukses generik ("Jika akun terdaftar, tautan reset telah dikirim") — ini mencegah user enumeration, jangan bocorkan apakah akun ada.
Jika user ditemukan: generate token acak (crypto.randomBytes(32).toString('hex')), simpan hash token (bukan token mentah) + expiresAt (15–30 menit) ke tabel PasswordResetToken, kirim email sungguhan berisi tautan /{locale}/auth/reset-password?token=....
Endpoint ini wajib dibatasi rate limit yang sama ketatnya dengan endpoint registrasi.
Halaman reset: form password baru + konfirmasi → POST /api/auth/reset-password dengan { token, newPassword }. Server hash ulang token yang diterima, cocokkan ke database, cek belum kedaluwarsa & belum dipakai, update passwordHash, tandai token usedAt, dan invalidasi token-token lain milik user tersebut.
Token bersifat sekali pakai. Setelah reset berhasil, arahkan ke halaman login dengan notifikasi sukses.
5.2 Middleware & Arsitektur Proteksi Akses (RBAC)
Arsitektur proteksi akses dan pengalihan rute dibagi menjadi dua lapisan utama untuk mencegah infinite redirect loop dan kegagalan status i18n:

1. Layer Middleware (`middleware.ts`):
   - Difokuskan khusus untuk menangani routing internasionalisasi (`next-intl`) berbasis cookie `NEXT_LOCALE` atau header `Accept-Language`.
   - Menjamin seluruh URL memiliki prefix locale yang valid (`/id/` atau `/en/`) tanpa memicu pengalihan berulang (infinite redirect) saat sesi NextAuth berakhir atau token kedaluwarsa.

2. Layer Server Component Layout Wrappers (`requireRole`, `requireActiveSubscription`):
   - Proteksi Peran Pengguna (RBAC - `SUPERADMIN` vs `USER`) diselenggarakan secara aman dan dinamis pada Server Component Layout (`src/app/[locale]/admin/layout.tsx` dan `src/app/[locale]/dashboard/layout.tsx`).
   - Tanpa token / Sesi habis + akses `/dashboard*` atau `/admin*` -> Redirect ke `/auth` dengan parameter `callbackUrl`.
   - Token ada, role `USER`, akses `/admin*` -> Redirect otomatis ke `/dashboard`.
   - Token ada, role `SUPERADMIN`, akses `/dashboard*` -> Redirect otomatis ke `/admin`.
   - Token ada, akses `/auth` -> Redirect otomatis ke rute utama sesuai peran (`/admin` untuk SUPERADMIN, `/dashboard` untuk USER).
   - Wajib divalidasi bahwa `NEXTAUTH_SECRET` tersedia di environment variable saat build/start.
5.3 Manajemen Profile Channel
CRUD penuh untuk ProfileChannel (tambah/edit/hapus/lihat), termasuk manajemen Product (katalog produk) di dalam tiap channel.
Jumlah channel yang boleh dibuat dibatasi oleh plan.maxChannels milik user (dibaca dari database, bukan hardcode).
Penguncian channel (isLocked) berjalan otomatis lewat fungsi enforceChannelLimits(userId) yang dipanggil setiap kali: langganan disetujui/berubah paket, langganan kedaluwarsa terdeteksi (lewat getSubscriptionState), atau admin mengubah paket user secara manual.
Urutkan channel berdasarkan lastUsedAt menurun; jumlah maxChannels teratas tetap aktif, sisanya dikunci (isLocked: true).
Channel terkunci tetap terlihat (read-only) di UI dengan indikator jelas, tidak dihapus, supaya user bisa membuka kunci begitu upgrade/perpanjang.

Fungsi generator (generateMasterPrompt) merakit prompt 2-Tahap (2-Stage AI Interaction Flow) selaras dengan aplikasi Push:
  - Tahap 1: Jika judul spesifik belum ditentukan user, AI menawarkan 10 rekomendasi judul berpotensi viral beserta persentase potensi viralitasnya di chat box AI eksternal, lalu berhenti sementara meminta konfirmasi nomor pilihan (1-10) dari user.
  - Tahap 2: Setelah user membalas nomor pilihan di chat box AI, AI mengeksekusi dan mengeluarkan output JSON valid murni (tanpa markdown fence) dengan skema: opsi_judul (10 judul rekomendasi Tahap 1), judul_konten (judul terpilih), caption_medsos, ide_thumbnail, html_blog, segments[] (tipe, visual, audio, narasi, durasi_estimasi).
  - Direktori Judul Terpakai: Hanya judul yang terpilih (draft.title) yang dimasukkan ke dalam direktori judul terpakai untuk excludeTitles pada prompt berikutnya; 9 opsi judul lainnya yang tidak dipilih tetap bersih dan tidak dikunci.
Sanitasi prompt: pastikan tidak ada instruksi developer yang bocor ke output (tidak ada judul yang di-hardcode secara kaku), sehingga hasilnya bisa langsung dipakai user ke ChatGPT/Claude/Gemini tanpa perlu diedit ulang.

B. Image Prompt Generator — WAJIB dibangun penuh, bukan placeholder

Form input terpisah: Profile Channel, Estetika Visual, Subjek/deskripsi utama gambar, Camera Type (DSLR/Mirrorless/Smartphone/Drone/Film), Shot Type (close-up/wide/macro/aerial), Lighting (natural/studio/golden hour/neon/dramatic), Mood, Color Grading, Visual Style (photorealistic/3D render/ilustrasi/claymotion/anime), Aspect Ratio, Negative Prompt (opsional), jumlah variasi prompt yang diinginkan.
Generator merakit prompt siap pakai untuk Midjourney/DALL-E/Stable Diffusion: gabungan tag deskriptif ringkas (dipisah koma) dan versi paragraf naratif, plus saran parameter (--ar, gaya) dan blok negative prompt bila diisi.
Hasil generate tersimpan sebagai Draft dengan type: IMAGE, sama seperti video.

Kedua mode berbagi komponen modal hasil (tampilkan teks, tombol salin ke clipboard, tombol simpan sebagai Draft).

5.5 Estimasi Durasi — Fitur Nyata, Dihitung dari Hasil AI

Ini bukan sekadar target input, tapi perhitungan pasca-generate yang sesungguhnya:

Saat user menempel/menyimpan hasil JSON dari AI eksternal ke Drafts, sistem mem-parsing seluruh field narasi di setiap scene, menjumlahkan total kata (wordCount), lalu menghitung estimatedDurationSec = wordCount / speakingRate (memakai speakingRate dari konfigurasi awal yang tersimpan bersama draft).
Tampilkan perbandingan jelas di UI: target durasi (dari form) vs estimasi durasi hasil AI (dihitung sistem), dengan indikator peringatan bila selisihnya signifikan (misalnya > 20%), agar user tahu naskahnya perlu dipangkas/ditambah.
5.6 Drafts / Riwayat — CRUD Penuh
GET /api/drafts (list milik user, dengan filter channel & type), POST /api/drafts (simpan hasil parse, termasuk wordCount/estimatedDurationSec dari 5.5), GET /api/drafts/:id, DELETE /api/drafts/:id. Tambahkan PATCH bila perlu edit judul/isi.
UI Drafts: tetap pertahankan AI JSON Parser (tempel JSON hasil dari AI eksternal, sistem mem-parsing ke editor scene per scene) tapi hasilnya benar-benar tersimpan ke database lewat endpoint di atas — bukan hanya di state lokal yang hilang saat refresh.
Daftar judul yang sudah pernah dipakai (untuk fitur "exclude judul" di Studio, 5.4) diambil otomatis dari Draft.title/parsedData.judul_konten milik channel terkait.

5.7.3 Alur Pembayaran Manual (aktif sekarang)

User memilih paket di halaman Billing → sistem menampilkan instruksi transfer memakai data dari AppSettings (nama bank, no rekening, atas nama — bukan hardcode di komponen).
User unggah bukti transfer (JPG/PNG, maks 2MB) → dikonversi base64 di client, divalidasi ulang di server (format MIME regex, ukuran ulang dihitung dari panjang base64, bukan cuma dipercaya dari client) → simpan sebagai Invoice dengan status: PENDING, method: MANUAL_TRANSFER, amount & planId diambil ulang dari tabel Plan di server, bukan dari body request (cegah user memanipulasi harga lewat devtools).
Endpoint ini wajib rate-limited per user.
Admin melihat daftar invoice pending (5.8), bisa lihat bukti transfer lewat endpoint khusus yang mendekode base64 jadi gambar, lalu Approve atau Reject.
Saat Approve (dalam satu transaksi Prisma, idempoten — tolak jika status invoice bukan lagi PENDING untuk mencegah approve ganda/race condition):
Invoice.status → APPROVED.
User.currentPlanId → invoice.planId, subscriptionStatus → ACTIVE.
subscriptionExpiresAt = jika sebelumnya masih aktif, tambahkan periodDays (default 30) ke tanggal expired lama (akumulatif); jika sudah expired/belum pernah, mulai dari sekarang + periodDays.
Panggil enforceChannelLimits(userId) untuk membuka kunci channel sesuai paket baru.
Saat Reject: Invoice.status → REJECTED, tidak ada perubahan apapun ke user.

6. STANDAR KEAMANAN (Checklist Wajib)

Terapkan semua poin berikut secara merata di seluruh endpoint yang relevan — bukan hanya sebagian:

Rate limiting pada semua endpoint sensitif: registrasi, cek ketersediaan akun, login (authorize() NextAuth), lupa password, reset password, submit pembayaran, generate prompt, pembuatan channel/produk. Kunci pembatas memakai kombinasi identifier + IP.
Jika hanya bisa memakai rate limiter in-memory (per-instance) untuk MVP, tulis komentar eksplisit di kode yang menjelaskan keterbatasannya (tidak konsisten di lingkungan multi-instance/serverless) dan tetap pasang di titik paling kritikal seperti login. Bila tersedia Redis/Upstash atau tabel database, gunakan penyimpanan persisten agar konsisten lintas instance.
Proteksi rute berlapis di middleware (5.2) DAN pengecekan ulang session.role/session.user.id di setiap route API — jangan hanya mengandalkan middleware.
Anti double-submit / race condition: kunci form dengan fieldset disabled={loading} di client, dan gunakan transaksi/updateMany dengan kondisi status di server (seperti pola approve invoice di 5.7.3) agar aksi ganda tidak bisa lolos meski client gagal mengunci.
Validasi kadaluarsa langganan di server, dieksekusi ulang setiap kali (bukan hanya sekali saat login) melalui requireActiveSubscription (3.4), dipanggil di setiap endpoint yang butuh langganan aktif, bukan hanya satu endpoint saja.
Uniqueness case-insensitive untuk username/email di query pengecekan maupun constraint aplikasi.
Kepatuhan atribut DOM/autocomplete standar W3C pada semua input form.
Validasi input ketat dengan zod (atau setara) di setiap route API — tolak payload yang tidak sesuai skema sebelum menyentuh database.
Upload file (bukti transfer): validasi MIME type via regex pada data base64, batasi ukuran di server (hitung ulang dari panjang string base64, jangan percaya Content-Length dari client saja), jangan simpan file mentah yang bisa dieksekusi.
Tidak percaya data harga/tier dari client (lihat 5.7.3 langkah 2).
Environment variables tervalidasi saat start: DATABASE_URL, NEXTAUTH_SECRET, kredensial email — aplikasi gagal cepat dengan pesan jelas jika salah satu kosong, bukan error samar saat runtime.
Tidak ada secret di kode atau log, .env* masuk .gitignore, siapkan .env.example tanpa nilai asli.
Seed data produksi: buat prisma/seed.js/seed.ts yang menginjeksi minimal: 1 akun SUPERADMIN, baris Plan untuk STANDARD/PRO/ULTRA, 1 baris AppSettings awal — agar server produksi tidak "kosong" saat pertama kali deploy (database baru tanpa data akan membuat login pertama gagal jika tidak diantisipasi).

Bagian 15: BROADCAST NOTIFICATION & DEDUPLICATION (Audit Remediation #39)
================================================================================
15.1. Field broadcastGroupId pada Model Notification
- Field tambahan: `broadcastGroupId String?` pada model `Notification` (prisma/schema.prisma).
- Diisi dengan UUID unik saat admin membroadcast pengumuman (POST /api/admin/announcements) ke seluruh user melalui fungsi `notifyAllSuperadmins`.
- Tujuan: mengelompokkan entri Notification yang merupakan satu batch broadcast, agar histori pengumuman di Admin Dashboard dapat ditampilkan secara ringkas (groupBy broadcastGroupId + recipientCount), bukan spamming per user.
- GET /api/admin/announcements: menggunakan Prisma `groupBy` pada `broadcastGroupId` + agregasi `_count` untuk menampilkan satu baris per pengumuman dengan jumlah penerima.
- Jika `broadcastGroupId` null (notifikasi sistem non-broadcast), entri tersebut tetap tersimpan secara individual.

15.2. Schema Change Changelog
- Migration: `prisma db push` (schema-first, no migration files — konsisten dengan lingkungan dev/Coolify).
- Kompatibel mundur: field nullable tidak mempengaruhi notifikasi yang sudah ada.

### Camera Movement — Tier Standar vs Profesional (PRO)

**Latar Belakang:**
Fitur Camera Movement tersedia dalam dua tingkatan kualitas berdasarkan paket user:

**1. Mode AUTO Standar (semua paket):**
Ketika toggle Camera Movement ON dan user tidak memilih preset/konsep kustom, AI bebas memilih gerakan kamera dari daftar referensi sederhana. Perilaku ini tidak berubah dan tetap tersedia untuk semua paket.

**2. Mode AUTO Profesional / PRO (paket PRO & ULTRA, dapat diatur admin):**
Ketika kondisi AUTO yang sama terpenuhi dan plan user memiliki entitlement `cameraMovementPro: true`, AI bertindak sebagai Director of Photography profesional dengan 8 prinsip:
1. Motivated Movement — setiap gerakan harus punya alasan naratif/emosional.
2. Tata Bahasa Gerakan per Peran Scene (Hook/Body/Klimaks/CTA).
3. Kosakata Gerakan Profesional (dolly, Steadicam, rack focus, dll).
4. Kontinuitas Antar-Scene — irama gerakan mengikuti busur emosi naskah.
5. Koordinasi dengan Blocking Subjek.
6. Kedalaman Visual (depth/parallax dengan foreground-midground-background).
7. Variasi Disengaja, Bukan Acak.
8. Format Wajib: [Jenis Gerakan] + [Kualitas/Kecepatan] + [Konteks Naratif].

**Mode KURASI USER** (preset atau custom concept dipilih): Perilaku tidak berubah untuk kedua tier.

**Prinsip Desain & Keamanan:**
- Entitlement `cameraMovementPro` divalidasi **hanya di server** (`api/generate/route.ts`) — tidak pernah dari body request client (fail-closed by design).
- Default flag: `false` (fail-closed) — paket tanpa konfigurasi eksplisit TIDAK mendapat PRO.
- SUPERADMIN selalu mendapat PRO.
- Admin mengatur entitlement per paket via Admin Panel → Plans → toggle "Camera Movement Profesional (PRO)".
- Seed default: DEMO=false, STANDARD=false, PRO=true, ULTRA=true.

**File Terkait:** `src/lib/planFeatures.ts`, `src/app/api/generate/route.ts`, `src/lib/promptGenerator.ts`, `src/components/generator/GeneratorForm.tsx`, `prisma/seed.js`.
